# 0001 — Хранилище в памяти процесса с потерей состояния при рестарте

Сервис бронирования хранит типы встреч и записи. ТЗ прямо разрешает in-memory при условии README-дисклеймера о потере состояния; альтернатива — лёгкая встраиваемая БД (SQLite через `better-sqlite3`). Выбираем in-memory с явным дисклеймером в README и откладываем миграцию на БД в следующую итерацию.

## Status

accepted

## Контекст

Развёртывание планируется как однопроцессное контейнерное приложение. Хранить данные нужно в пределах одного процесса; доменная модель проста — два типа сущностей, отношения «один-ко-многим» между типом встречи и записями. ТЗ явно допускает in-memory вариант.

## Альтернативы

- **SQLite через `better-sqlite3`**: обеспечивает переживание рестарта, требует миграций и схемы. Не выбрано для v1, чтобы остаться в рамках «небольшое, но законченное приложение» и не наращивать рантайм-зависимости.
- **In-memory без локов (полагаться на однопоточность Node.js)**: короче в коде, но хрупко при будущей миграции на БД и при усложнении логики записи. Принципиально не выбрано.

## Следствия

- Любой рестарт процесса или контейнера (`docker restart`, `railway redeploy`, ручной `npm run start`) стирает все типы встреч и записи.
- Тесты на пересечения слотов и конкурентность тривиально воспроизводятся в `vitest` без поднятия БД.
- Переход на SQLite возможен без изменения OpenAPI-контракта (`spec/`) — меняется только реализация `BookingStore` в `src/store/`.
- README должен содержать раздел «Ограничения» с явным дисклеймером.
