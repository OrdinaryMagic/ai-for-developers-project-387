# 0002 — Один AsyncLock на BookingStore: всё под одним мьютексом, acquire/release — шов под SQLite-транзакцию

ADR-0001 фиксирует in-memory-хранилище и откладывает миграцию на SQLite, но саму конкурентность в `BookingStore` как отдельное решение не закрепляет. Закрываем этот пропуск: выбираем один FIFO-мьютекс на стор, оборачиваем им все мутации и снимко-чтения, фиксируем `acquire/release` как шов под будущую транзакцию.

## Status

Принято (`accepted`) в рамках ticket #6. Закрывает отложенный в ADR-0001 вопрос «конкурентность в BookingStore» и фиксирует шов `acquire/release` под будущую миграцию на SQLite-транзакцию (ADR-0001 deferral). Решение будет пересмотрено при появлении нагрузки, требующей write-throughput выше того, что даёт один мьютекс, либо при переходе к multi-instance deploy.

## Контекст

ADR-0001 фиксирует, что хранилище живёт в памяти одного Node.js-процесса, и явно откладывает миграцию на SQLite (через `better-sqlite3`) в следующую итерацию. В том же решении есть формулировка «без сложной per-key логики» — она отсылает к вопросу конкурентности, но саму конкурентность как отдельное решение не закрепляет.

Между тем `BookingStore` (см. `src/store/booking-store.ts`) уже сейчас принимает конкурентные запросы: два параллельных `POST /bookings` на один и тот же `Slot` должны приводить ровно к одной успешной записи и одному ответу с `code: "SLOT_TAKEN"` (см. `Idempotency Policy` в `GLOSSARY.md` и `Domain Error` с кодами `SLOT_TAKEN` / `MEETING_TYPE_NOT_FOUND` / `OUTSIDE_WORKING_HOURS` / `OUTSIDE_WINDOW` / `MISMATCH_STEP`). Календарь занятости (см. термин `Slot`) — per-slot exact: между `book()` и параллельным `availability()` нельзя наблюдать промежуточное состояние, в котором слот одновременно свободен и занят.

Очевидный следующий шаг, который напрашивается — **per-key lock**: отдельный мьютекс на каждый `Slot` (или хотя бы на каждый `meetingTypeId`). Идея выглядит привлекательно, потому что снимает теоретический bottleneck единого мьютекса, и её легко обосновать «масштабируемостью». Настоящий ADR закрывает отложенный вопрос: почему для v1 мы сознательно остаёмся на одном мьютексе.

## Решение

В `src/store/async-lock.ts` живёт минимальный FIFO-мьютекс с интерфейсом `acquire()` → `release()` (одна hold-точка, очередь жёсткая: каждый следующий `acquire()` ждёт `release()` предыдущего, повторное использование одного и того же мьютекса внутри одного процесса deadlock-невозможно).

`BookingStore` хранит ровно один экземпляр этого мьютекса (`private readonly gate = new AsyncLock();`) и оборачивает им:

1. **Каждую мутацию** — на сегодня это `book()` целиком, секция «проверка пересечения + `bookings.push`» под `await this.gate.acquire()` / `try { ... } finally { release(); }`. Невалидный ввод (`MEETING_TYPE_NOT_FOUND`, `OUTSIDE_WORKING_HOURS`, `OUTSIDE_WINDOW`, `MISMATCH_STEP`) отдаётся до входа в критическую секцию — под лок заходим только ради атомарной пары `check conflict → push`.
2. **Каждое снимко-чтение**, которое отдаётся через слой маршрутов, — на сегодня это `snapshot()` (`this.bookings.slice()` под тем же `gate`), из которого `list()` и `availability()` строят свои представления. Метод приватный, чтобы добавить новое снимко-чтение без лока было нельзя без правки стора.

Обоснование:

- **Масштаб v1 это оправдывает.** Один `Owner`, in-memory-хранилище, узкое место — теоретическое. На нагрузке v1 (десятки записей в день, не тысячи в секунду) сериализация всех мутаций через один мьютекс не видна ни в latency, ни в throughput. Усложнение ради гипотетической нагрузки преждевременно.
- **Per-key lock не оправдан на этой нагрузке.** Per-key требует: (а) маршрутизации lock-ключа из доменной логики — какой именно ключ для слота? `meetingTypeId` слишком грубо (слоты пересекаются между типами), `startsAt`-миллисекунды слишком точно (гость не передаёт «ключ»); (б) явного упорядочения при захвате двух ключей, чтобы исключить deadlock; (в) очистки при устаревании слота за пределами `Window`. Это всё лишняя поверхность атаки на баги, не заработанная нагрузкой.
- **`acquire/release` — это шов под будущую транзакцию.** ADR-0001 откладывает миграцию на SQLite; интерфейс `AsyncLock` (`acquire()` возвращает функцию `release`, холдер обязан вызвать её в `finally`) семантически совпадает с `BEGIN ... COMMIT`. Когда ADR-0001 закроется, `gate` в `BookingStore` останется той же ручкой, а его реализация сменится на транзакцию `better-sqlite3`. Контракт стора наружу не движется.

## Альтернативы

- **Per-key lock (мьютекс на каждый слот / на каждый `meetingTypeId`).** Отвергнут: на нагрузке v1 не нужен, добавляет маршрутизацию ключа, риск deadlock-ов при захвате двух ключей и стоимость очистки для слотов за пределами `Window`. Не заработан входящим потоком.
- **Event-sourced command queue (очередь команд с последовательной обработкой).** Отвергнут как out of scope: ADR-0001 явно фиксирует, что мы избегаем новых рантайм-зависимостей и сложных паттернов в v1; очередь команд потребовала бы персистентного лога и инфраструктуры replay, что принадлежит следующей итерации наряду с переездом на БД.
- **Read/write split с eventual consistency для `availability()`.** Отвергнут: календарь занятости — per-slot exact (см. `Idempotency Policy` и `Slot` в `GLOSSARY.md`); допускать чтение «слот ещё свободен» после того, как `book()` уже отдал слот, значит множить ошибки UX. Сложность eventual consistency (версии, откаты, рассогласование `list`/`availability`) не оправдана в домене, где точность per-slot — базовое требование.

## Следствия

Положительные:

- **Детерминированные снимки.** `availability()` всегда согласован с результатом последнего завершённого `book()`: либо слот ещё свободен, либо уже занят. Никаких частичных наблюдений «слот отдан в массив, но ещё не виден в `availability`».
- **Простая модель рассуждений.** В любом месте `BookingStore` состояние либо «до моего хода», либо «после моего хода» — никаких промежуточных видимых состояний. Тесты на конкурентность (`test/store/booking-store.test.ts` и связанные) тривиально воспроизводятся без поднятия реальной БД.
- **Deadlock-свободно по построению.** Один мьютекс — один владелец в один момент времени, графа захвата нет.
- **Перенос на SQLite без изменения контракта стора.** `acquire/release` остаётся публичной ручкой; реализация `gate` меняется, сигнатуры методов `BookingStore` — нет.

Отрицательные:

- **Сериализация мутаций ограничивает write-throughput.** Все конкурентные `POST /bookings` идут в одну очередь. На v1-нагрузке это не заметно, но если в следующей итерации появится сценарий «тысячи попыток записаться в момент открытия окна» — узкое место станет видимым и придётся пересматривать решение (см. ниже).
- **Multi-instance deploy расходится по состоянию.** Один процесс = одно представление `BookingStore`. Горизонтальное масштабирование «поставлю второй контейнер за балансером» не работает: каждый процесс видит свой массив `this.bookings`, и два гостя, попавшие в разные контейнеры, оба получат `200 OK` на один и тот же `Slot`. Это требует либо sticky-routing на одного владельца, либо (что реалистичнее) — миграции на общее хранилище (ADR-0001 deferral).
- **`list()` и `availability()` ходят под локом.** Чтения тоже сериализуются, хотя между собой они не конфликтуют. Это сознательная жертва: проще держать один мьютекс, чем поддерживать отдельный read-lock и рассуждать о snapshot isolation руками.
