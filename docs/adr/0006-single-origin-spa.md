# 0006 — Фронтенд и API в одном сервисе (один origin)

Живой деплой на Railway (ADR-0005) отдавал только API: `GET /admin/event-types` и любые
клиентские маршруты возвращали 404, потому что в образ попадал только backend — фронтенд
(`web/`) собирался отдельно и в контейнер не копировался. Размещение «одного домена под
продукт» требовало, чтобы по тому же адресу открывался интерфейс. Принимаем решение: **собранный
SPA отдаёт тот же сервис, что и API** — один origin, один деплой, один домен.

## Status

accepted (дополняет [ADR-0005](0005-hosting-platform-railway.md))

## Контекст

- **Продукт — не только API.** Карта #26 («UI & E2E») дала фронтенд: React + Vite + shadcn/ui
  в отдельном workspace `web/` (AGENTS.md rule #10). Клиентские маршруты живут только в
  браузере: `/`, `/book/:meetingTypeId`, `/book/:meetingTypeId/confirmed`, `/admin/bookings`,
  `/admin/event-types`. Сервер о них не знает и знать не должен.
- **Домен один.** Развёртывание — Railway, платформенный домен `*.up.railway.app`
  (ADR-0005). Отдельный домен под фронтенд означал бы второй сервис, второй деплой и
  cross-origin запросы к API.
- **Фронтенд уже говорит с API по `/api/*`.** Это конвенция dev-прокси Vite
  (`web/vite.config.ts`: `/api/*` → Fastify **без** префикса). В production Vite-прокси нет —
  префикс должен снимать кто-то. Значит, Either API живёт под `/api/*`, либо backend делает
  алиас.
- **Канонический контракт API нельзя ломать.** `spec/*.tsp` описывает пути без префикса
  (`/config`, `/meeting-types`, `/bookings`), и `openapi.yaml` генерируется из спеки
  (AGENTS.md rule #9). Менять пути в спеке — значит ломать публичный контракт v1 и генерировать
  SDK заново.
- **Технически это один Node-процесс.** Fastify умеет отдавать статику
  (`@fastify/static`), а SPA-fallback (отдача `index.html` на клиентский маршрут) —
  обычный `setNotFoundHandler`.

### Что не работало

- **Отдельный статический деплой** (S3 / Pages / отдельный Railway-сервис): второй origin →
  CORS-заголовки, отдельный TLS и домен, публикация `dist` отдельным шагом пайплайна. Для v1
  с одним владельцем — лишняя сущность без выигрыша.
- **Прокси перед обоими** (nginx/traefik рядом с API): ещё один сервис в карте, ещё один
  health-check, ещё одна точка отказа. При этом Railway даёт managed TLS и edge сам.
- **Пути API с префиксом `/api` в спеке**: ломает публичный контракт v1 (`openapi.yaml`
  регенерируется → SDK перегенерируется → фронтенд переписывается).

## Решение

Принимаем **«один сервис — один origin»**: Fastify отдаёт и API, и собранный SPA.

### Раскладка маршрутов

| Путь                                        | Кто отвечает                                                           |
| ------------------------------------------- | ---------------------------------------------------------------------- |
| `/config`, `/meeting-types`, `/bookings`, … | API (канонические пути, как в `spec/*.tsp`)                            |
| `/api/*`                                    | тот же API (алиас, снимает префикс)                                    |
| `/assets/*`                                 | статика сборки `web/dist`                                              |
| `/`                                         | JSON `{"hello":"world"}` для API-клиентов, оболочка SPA — для браузера |
| `/admin/event-types`, `/book/:id`           | оболочка SPA (SPA-fallback), а не 404                                  |

Три правила, на которых держится раскладка:

1. **Канонические пути API не меняются.** Специфичный маршрут Fastify всегда выигрывает у
   wildcard'а статики, поэтому `/meeting-types` остаётся API-маршрутом, а не файлом из `dist`.
   `spec/*.tsp` и `openapi.yaml` не трогаем.
2. **Алиас `/api/*` — это алиас, а не новый контракт.** API смонтирован дважды: под
   каноническим префиксом и под `/api` (`src/app.ts`, плагин `src/routes/api.ts`). Оба
   монтирования делят одни и те же сторы, поэтому состояние не расходится: запись, созданная
   через `/api/bookings`, видна в `/bookings`.
3. **Кто браузер — определяет заголовок `Accept`.** Браузерная навигация шлёт
   `Accept: text/html` и получает оболочку приложения; API-клиенты (`fetch`, `curl`,
   smoke-скрипт) получают JSON. Поэтому контракт `GET /` → `{"hello":"world"}` (часть
   OpenAPI-спеки) остаётся в силе, а `/` в браузере открывает интерфейс. 404 под `/api/*`
   остаётся JSON-ответом: SPA-fallback не должен превращать ошибку API в HTML.

### Сборка

`Dockerfile` получил отдельную стадию `web-builder`: `npm ci` в `web/` (свой lockfile) →
`vite build` → готовый `web/dist` копируется в runtime-образ в `/app/web/dist`. Путь
`defaultStaticRoot()` (`src/static-ui.ts`) указывает именно туда — и в dev, и в контейнере.
`.dockerignore` больше не исключает `web/` целиком: исходники фронтенда нужны на сборке,
локальные артефакты (`web/dist`, `web/node_modules`, `web/.vite`) — нет.

### Проверка

- `test/static-ui.test.ts` — контракт раздачи статики: ассет с immutable-кэшем, оболочка на
  клиентском маршруте, JSON-404 для API-клиента, алиас `/api/*` и общее состояние сторов.
- `scripts/production-smoke.sh` — post-deploy smoke (ADR-0005) получил две UI-проверки:
  `GET /` и `GET /admin/event-types` с `Accept: text/html` должны вернуть 200 и
  `content-type: text/html`. Без них «деплой поднялся, но статики нет» был бы зелёным.

## Альтернативы

### Отвергнуты

- **Отдельный статический деплой (S3 / Pages / второй сервис Railway)** — второй origin, CORS,
  второй деплой и вторая точка отказа. Для v1 с одним владельцем выигрыша нет.
- **Reverse-proxy перед API и статикой** — ещё один сервис, ещё один health-check; managed TLS
  и edge Railway уже дают.
- **Перенести канонические пути API под `/api/*`** — ломает публичный контракт v1
  (`openapi.yaml` → SDK → фронтенд) ради локального удобства.

### Рассмотрены и отвергнуты структурно

- **SSR/гидратация на сервере** — в v1 нет данных для рендера на сервере (состояние в памяти,
  один владелец), а SSR-фреймворк в Node-стеке добавил бы рантайм-зависимость и отдельный
  билд-пайплайн. Клиентский рендер SPA достаточно.
- **Рендерить UI отдельным микрофронтендом на другом домене** — то же, что отдельный
  статический деплой, только дороже.

## Следствия

- **Публичный адрес один.** `https://booking-api-production-b3a4.up.railway.app` открывает и
  API, и интерфейс; отдельного домена под UI нет и не планируется.
- **CORS не нужен** — фронтенд и API на одном origin. Если UI всё же отдаётся с другого
  домена (например, локально из Vite), запросы идут через dev-прокси `/api/*`, и это
  остаётся dev-механизмом, а не production-контрактом.
- **Образ тяжелее.** В образ попадает собранный фронтенд (~350 KB JS + ~14 KB CSS в gzip
  меньше). Для Railway с лимитом 500 MB это несущественно, но образ больше, чем «backend-only».
- **Кэширование.** Ассеты Vite хэшированы по содержимому → `public, max-age=31536000,
  immutable`. Оболочка (`index.html`) — `no-cache`: она меняется вместе с новым деплоем, и
  закешированная оболочка ссылалась бы на старые ассеты.
- **Smoke-скрипт стал строже** (6 проверок вместо 4) — «деплой поднялся, но UI не отдаётся»
  теперь ловится на post-deploy шаге, а не глазами в браузере.
- **Единственный источник правды о статике — `web/dist`**, собираемый из `web/`; руками
  собранные файлы в образ не попадают.

## Что НЕ меняется этим ADR

- ADR-0001 (in-memory store), ADR-0002 (single-writer), ADR-0003 (release-please),
  ADR-0005 (платформа размещения, Railway).
- AGENTS.md rule #9 (generated-артефакты), rule #10 (`web/` — отдельный workspace),
  rule #11 (SDK — единственный источник API-типов на клиенте).
- OpenAPI-контракт (`spec/*.tsp` → `openapi.yaml` → `web/src/api/sdk.ts`): пути API не
  менялись, регенерация не требуется.
