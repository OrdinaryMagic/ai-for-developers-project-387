# Доменная документация

Как инженерные скиллы должны читать доменную документацию этого репозитория во время исследования кодовой базы.

## Перед исследованием прочитай

- **`GLOSSARY.md`** в корне репозитория, либо
- **`GLOSSARY-MAP.md`** в корне репозитория, если он существует: указывает на отдельные `GLOSSARY.md` для каждого контекста. Читай релевантные теме контексты.
- **`docs/adr/`**: прочитай ADR-ы, касающиеся области, в которую ты собираешься лезть. В мульти-контекстных репозиториях также проверь `src/<context>/docs/adr/` для контекстно-локальных решений.

Если какого-то из этих файлов нет — **продолжай молча**. Не сигналь об отсутствии, не предлагай создавать их на старте. Скилл `/domain-modeling` (вызывается через `/grill-with-docs` и `/improve-codebase-architecture`) создаёт их лениво, когда термины или решения реально появляются.

## Структура файлов

Single-context репозиторий (большинство репозиториев):

```
/
├── GLOSSARY.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

Мульти-контекстный репозиторий (наличие `GLOSSARY-MAP.md` в корне):

```
/
├── GLOSSARY-MAP.md
├── docs/adr/                          ← общесистемные решения
└── src/
    ├── ordering/
    │   ├── GLOSSARY.md
    │   └── docs/adr/                  ← решения в контексте
    └── billing/
        ├── GLOSSARY.md
        └── docs/adr/
```

## Используй лексику глоссария

Когда в выводе ты называешь доменное понятие (в заголовке задачи, предложении рефактора, гипотезе, имени теста) — используй термин в том виде, в каком он определён в `GLOSSARY.md`. Не сбивайся на синонимы, которые глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо ты придумываешь язык, которого в проекте нет (подумай ещё раз), либо есть реальный пробел (отметь для `/domain-modeling`).

## Сигналь о конфликтах с ADR
